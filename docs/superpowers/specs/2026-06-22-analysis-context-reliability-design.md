# Analysis Context Reliability Design

## Goal

Introduce a versioned analysis context contract that tells every downstream
consumer whether market, financial, and RAG inputs are available, missing,
unsupported, stale, estimated, partial, fallback data, or failed fetches.

This phase improves reliability without replacing the existing graph fields or
changing current API clients.

## Scope

This phase includes:

- Pydantic models for context status, context items, data quality, and the
  top-level analysis context pack.
- A context builder that converts existing market, financial, and RAG results
  into the new contract.
- An `analysis_context` field in graph state and analysis API responses.
- Compatibility tests proving all existing response fields remain available.
- Unit tests for status classification and data-quality scoring.

This phase excludes:

- Strict citation gating.
- Persistent background tasks.
- Expanded tracing, scheduling, notifications, portfolio risk, or backtesting.
- Broad rewrites of individual agents.

## Data Contract

### ContextStatus

The supported values are:

- `available`: usable primary data is present.
- `missing`: data should exist but is absent.
- `not_supported`: the current market or provider does not support the data.
- `fallback`: mock or lower-quality fallback data is being used.
- `stale`: data exists but is older than its accepted freshness window.
- `estimated`: the value was derived rather than directly observed.
- `partial`: only part of the expected data is available.
- `fetch_failed`: an attempted external fetch failed.

### ContextItem

Each input block contains:

- `status`
- `value`
- `source`
- `timestamp`
- `fallback_from`
- `missing_reason`
- `warnings`
- `metadata`

`value` remains flexible because the existing market, financial, and RAG
payloads have different shapes. Status and provenance remain strongly typed.

### DataQuality

The quality summary contains:

- `overall_score`, from 0 to 100.
- `level`: `good`, `usable`, `limited`, or `poor`.
- `limitations` and `warnings`.

The initial score is deterministic and based only on block status. Available
blocks score highest; partial, estimated, stale, and fallback blocks reduce the
score; missing, unsupported, and failed blocks reduce it further. The builder
must not infer quality from prose generated by an LLM.

### AnalysisContextPack

The top-level contract contains:

- Fixed `version` value `1.0`.
- `company`.
- `market`, `financials`, and `rag` context items.
- `data_quality`.
- UTC `created_at`.

## Classification Rules

Market and financial profiles use explicit machine-readable fields before
examining human-readable reason text.

- A successful enabled payload with substantive values is `available`.
- An unsupported market or instrument is `not_supported`.
- An attempted provider failure is `fetch_failed`.
- An empty payload without an attempted fetch is `missing`.
- A payload explicitly marked as fallback is `fallback`.
- An incomplete but useful payload is `partial`.

RAG classification uses document metadata:

- Any mock-only result is `fallback`.
- Empty retrieval output is `missing` unless a fetch failure is recorded.
- A mixture of usable and fallback chunks is `partial`.
- Usable non-mock chunks are `available`.

No mock, fallback, empty, or failed input may be classified as `available`.

## Integration

A new context builder receives the existing `market_profile`,
`financial_profile`, and RAG context. It returns an `AnalysisContextPack`.

The graph constructs the pack after RAG retrieval, when all three input groups
are available. It stores the serialized pack in `DeepAlphaState` as
`analysis_context`. Downstream nodes can read it immediately, but this phase
does not rewrite every agent prompt.

The full analyze response adds `analysis_context`. Existing fields including
`market_profile`, `financial_profile`, `rag_chunks`, `agent_outputs`, and
`final_decision` remain unchanged. Report-focused responses remain unchanged in
this phase unless their declared response model already exposes the full graph
state.

## Error Handling

The context builder must be total for normal graph inputs: malformed or absent
optional payloads produce a typed degraded status rather than raising an
exception that aborts analysis.

Programming errors and invalid contract versions should still raise during
development and tests. External error messages may be retained in metadata for
diagnostics, but secrets and credentials must never be copied into the context.

## Testing

Tests are written before implementation and cover:

- Successful market data becomes `available`.
- Mock-only RAG data becomes `fallback`.
- Provider failure becomes `fetch_failed`.
- Unavailable financial data becomes `missing` or `not_supported` according to
  explicit provider semantics.
- Fallback and failed blocks reduce the deterministic quality score.
- The analysis response includes `analysis_context` while retaining all
  existing fields.
- Existing API tests continue to pass.

Verification for this phase is the complete Python test suite and the frontend
production build.

## Compatibility And Rollback

The API change is additive. No existing field is removed or renamed, and agent
input dictionaries remain available while consumers migrate.

Rollback consists of removing the builder call, the additive graph/API field,
and the new schema module. Existing analysis behavior remains intact because
the old fields are not replaced.
